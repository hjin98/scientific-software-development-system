## 4. Lessons for the next repair round

- Most blockers since `e9e6e9f` entered through the previous round's repairs, often of non-blocking suggestions. Apply non-blocking suggestions only when they are wording, disclosure, or strictly adverse-only enlargement; check every new clause for siblings before freezing (two real holes were caught this way: `bound` vacuous for unbounded bases; submodule materialization).
- A green diagnostic covers only what it models: the a6ed164 blocker (equivalence-path aggregation) lay outside the judgment model's three kinds. When a Review finds a defect, extend the model to reproduce it before repairing, and state the model's claims as narrowly as its cases.
- A Review's recommended option is a hypothesis, not a repair: the lifecycle family recurred three times through adopted options. When a family recurs, model it first, with each earlier rule as a mutation, and state the rule as what is protected (a value) rather than as a mechanism (a set of identities).
- A rule that is a state machine must define every state's exits. Candidate 49 fitted its rule to a model whose event table omitted the transitions the next Review found; when modelling, enumerate exits per state (ready, waiting, routed, closed) rather than events, and prefer routing a hard case to an existing owner over a new automatic transition.
- Prefer subtractive repairs; several additive repairs (runner fallback, LFS exception, `qcap`, observed-read bounding, the identical-tree shortcut, the tenure filter) each produced the next blocker and were later removed.
